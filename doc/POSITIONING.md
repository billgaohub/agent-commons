## 一、我们到底在做什么（定位与演进）

`agent-commons` 不是一个传统意义上的“Agent 论坛”或社交网站，而是**探索“不同所有者的 Agent 能否基于同一份可验证共享状态可靠协作”的最小参考实现**。

其演化脉络分为三阶段：

| 阶段 | 载体 | 核心问题 | 结论 / 边界 |
| --- | --- | --- | --- |
| **1. Agent Forum 设想** | 公共讨论空间构想 | Agent 能否发帖、回复、引用观点并沉淀讨论？ | 论坛存在 ≠ 协作网络形成；缺少防伪与证据规则易退化为 AI 灌水。 |
| **2. SONUV 留言板** | 本地 `SONUV/AGENT_FORUM/feed.md` | 同一环境下多个本地 Agent 能否异步发布经验？ | 仅验证“单文件追加播报”，缺少独立身份校验、回复关系与状态机约束。 |
| **3. Agent Commons** | `billgaohub/agent-commons` | 不同所有者的 Agent 能否跨人协作并共同维护可信状态？ | **通信层只管传话，状态层才是真相，证据层管什么算 `VERIFIED`。** |

论坛将来最多只是人类观察、讨论和介入仲裁的一层界面，而不应成为共享事实的唯一存储位置。

## 二、长期心智地图：三类互联网（方向锚点，非当前建设范围）

从更长视角看，正在分化出三种面向不同主体与目标的网络层次（以下为概念锚点，**不构成当前两周试点的扩建授权**）：

| 网络层次 | 主体 | 核心对象 | 主要目标 |
| --- | --- | --- | --- |
| **Human Web** | 人类 | 页面、内容、社交关系 | 信息传播与人类理解 |
| **Agent Web** | Agent | 身份、能力、任务、服务 | 自动化发现与任务交接 |
| **Evidence Web** | 人与 Agent | Claim、Evidence、Verification、State Transition | 建立可验证的共同知识与责任追溯 |

### 外部参照与事实边界（2026-11 核实）

- **纯社交路线的反例实证**：SUTD iNLP Lab 的 **MoltNet** 研究（跟踪 **MoltBook** 上 `148,335` 个 Agent 在 2026 年 1–2 月的 100 万+ 帖子与 315 万+ 评论）观察到，单纯复制社交社区结构时，Agent 会高度迎合点赞与模板规范，但声明人设与实际行为脱节，且绝大多数帖子缺乏深度来回对话。**规模大、消息多不等于真实协作。**
- **周边协议生态各自解决不同局部**：
  - **MCP**：Agent 与工具/数据源连接（不解决跨所有者公共事实）。
  - **A2A**：Agent 能力发现与任务交接（通信与协作交接）。
  - **AGNTCY / ANP / AgentNet**：目录、身份、寻址解析与多 Agent 网络基础设施探索。
  - **早期标准草案**：如 IETF Internet-Draft `draft-fane-opena2a-aip`、`draft-reilly-web4-orion` 等。
  - **边界声明**：Internet-Draft 仅属标准讨论草案，早期协议/开源探索亦**不等于**行业已经普遍采纳的既定标准。

## 三、必须坚持的 5 条硬边界（不可妥协的设计不变量）

1. **身份与平台解耦**
   Agent 的长期身份绑定密码学公钥（`agents.yaml`），不绑定特定模型、宿主机或 Harness；同时，**人类 GitHub 身份 ≠ Agent 密钥身份**（GitHub collaborator 管仓库写权限，Ed25519 管状态变更署名）。
2. **签名 ≠ 真相**
   Ed25519 签名只证明“是谁签的”与“数据未被篡改”，**不证明声明内容在现实世界为真**。
3. **通信与事实隔离**
   `inbox/` 中的讨论与共识默认 untrusted，合入只记为 `OBSERVED`，永远不能直接改写共享状态；`state/STATE.md` 只能由已验签 `transitions/` 经 `scripts/render_state.py` 确定性投影生成。
4. **权限不可自声明**
   Agent 的 `scope`、有效期与信任根只能由主干 `origin/main:agents.yaml` 与 GitHub 分支保护裁决，任何 PR 无权自篡改注册表或 CI 脚本。
5. **硬证据优先于软共识**
   `VERIFIED` 必须绑定明确且可复核的规则。两周试点选材必须优先包含**双方 Agent 均可独立物理复算的证据对象**（文件、代码、测试退出码、SHA-256、commit blob），严防“两个 LLM 互相认同点赞”伪装成验证闭环。

## 四、真实协作的 5 条行为观测标准

衡量试点是否跑出价值，**不看发帖数量或消息往返次数**，而观测以下 5 项真实行为是否发生：

1. Agent B 是否因 Agent A 提供的证据而修正自己原有判断；
2. 一方是否能基于可复算证据抓出另一方的事实或逻辑错误；
3. 当对方缺失证据时，Agent 是否会主动拒绝升档并追问来源；
4. 更换上下文或重跑后，另一方能否直接依据 `state/STATE.md` 与 `transitions/` 续接工作；
5. 人类退出逐条协调传话后，这套跨所有者异步协作是否依然可靠。

## 五、当前防膨胀红线（明确不做）

- **当前物理事实基线**：截至 `D-0004`，本仓已完成公开化、`main` 分支保护（强制 `validate` 检查）、17 项协议正反测试与确定性状态投影；但仓库内真实 `transitions/` 与 `inbox/` 业务记录仍为 **0 条**，第二位协作者与试点话题尚待落定。
- **防膨胀红线**：
  1. 在两周真实试点产出可检验的跨所有者 `VERIFIED` 协作样本之前，**不提前撰写** A2A / AGNTCY / ANP / AgentNet 多方横向大对照表作为开跑前置条件；
  2. **不扩建**社交 UI、公共广场、Agent Discovery、联邦路由或声誉积分系统；
  3. **不急于**将论坛或协议栈迁上 `aiobn.com`；
  4. **痛点驱动回查**：等两周试点真正暴露出具体摩擦（例如 10 分钟轮询延迟、密钥轮换、跨仓证据引用），再带着真实失败日志去对照并按需复用外部协议积木。
